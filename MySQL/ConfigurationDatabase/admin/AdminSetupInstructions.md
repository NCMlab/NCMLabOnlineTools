# Admin Write API — Setup & Security Notes

> **Authorship notice**
> This document was generated by **Claude Code (model: claude-sonnet-5)** on **2026-07-08**.

This is the authenticated write API for **NCMBatteryWebsite** (a separate repo, a ReactJS
battery-builder UI) to create rows in `ncmbattery_config` — new `task_parameters`/
`task_instructions` sets, and new `batteries`/`battery_tasks`. It is deliberately separate from
`API_battery.php`/`API_task_config.php` in the parent folder, which stay public and read-only for
JATOS study pages. See `DiscussionLog.md` for the design discussion that led here.

---

## Why this is a separate, smaller surface than the public API

The public API has no login and `Access-Control-Allow-Origin: *` — appropriate for read-only
data that every study participant's browser needs. This API does the opposite on every axis:
requires a session, restricts CORS to one named origin, and only accepts `POST`. Never merge
these two APIs or relax the public one to also handle writes.

## Part 1 — Deploy the schema addition

`admin_users` was added to `CreateSchema.sql` (Table 8) as part of this work. If you already ran
`CreateSchema.sql` once, re-run it — every `CREATE TABLE` uses `IF NOT EXISTS`, so this is safe
and only adds the new table:

```bash
mysql -u ncmuser -p ncmbattery_config < MySQL/ConfigurationDatabase/CreateSchema.sql
```

## Part 2 — Create your first admin account

There is no HTTP registration endpoint on purpose — these are privileged lab-staff accounts, not
public sign-up. Run this **on the server**, not from a browser:

```bash
cd MySQL/ConfigurationDatabase/admin
php create_admin_user.php your_username
# prompts for a password (not echoed), requires 12+ characters
```

Re-running it for the same username updates their password (`ON DUPLICATE KEY UPDATE`). The
script refuses to run under a web server (`php_sapi_name() !== 'cli'` check), so it's safe even
if this folder ends up inside a web-accessible path by mistake.

## Part 3 — Configure and deploy the PHP files

Edit the same four DB constants as the public API, in **each** of these files: `admin_common.php`,
`create_admin_user.php`:

```php
define('DB_HOST', 'localhost');
define('DB_NAME', 'ncmbattery_config');
define('DB_USER', 'ncmuser');
define('DB_PASS', 'StrongPassword123!');
```

Then, in `admin_common.php` only, set the exact origin NCMBatteryWebsite will be served from —
**this cannot be `*`**, because these requests carry a session cookie and browsers reject
wildcard CORS on credentialed requests:

```php
define('ADMIN_ALLOWED_ORIGIN', 'https://battery-admin.your-lab.edu');
```

Deploy `admin_common.php`, `API_admin_login.php`, `API_admin_logout.php`, `API_admin_whoami.php`,
`API_admin_create_parameter.php`, `API_admin_create_instruction.php`,
`API_admin_create_battery.php` together to a folder on your PHP/Apache server (e.g.
`/var/www/html/api/admin/`). Also deploy the parent folder's `API_list_config.php` alongside the
existing public `API_battery.php`/`API_task_config.php` (e.g. `/var/www/html/api/`) — it's the
public, unauthenticated "what exists?" endpoint NCMBatteryWebsite uses to populate its task-type
grid and parameter-set dropdowns. Do **not** deploy `create_admin_user.php` to a web-accessible
path — keep it somewhere only reachable by SSH/CLI, even though it self-protects against HTTP
execution.

**HTTPS is not optional here.** The session cookie is marked `secure`, meaning browsers will
refuse to send it at all over plain HTTP — login will appear to silently fail. Put this behind
TLS before testing.

## Part 4 — How the frontend should call it

**This is implemented, not just a plan** — see `NCMBatteryWebsite/user-website/src/api.js`,
`AuthContext.js`, `Login.js` for the real client. The steps below describe what that code does.

1. `POST /api/admin/API_admin_login.php` with `{ "username", "password" }` and
   `credentials: 'include'` (so the browser stores/sends the session cookie). Save the
   `csrf_token` from the response in memory (not `localStorage` — see the note below).
2. On every subsequent write call (`API_admin_create_parameter.php`,
   `API_admin_create_instruction.php`, `API_admin_create_battery.php`), also send
   `credentials: 'include'` and header `X-CSRF-Token: <the saved token>`.
3. `GET /api/admin/API_admin_whoami.php` (`credentials: 'include'`) on app load, to recover
   login state and a fresh CSRF token after a page reload — the in-memory token from step 1
   doesn't survive a refresh even though the session cookie does.
4. `POST /api/admin/API_admin_logout.php` (`credentials: 'include'`) when the user logs out.

```js
const res = await fetch('https://your-server/api/admin/API_admin_login.php', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ username, password }),
});
const { csrf_token } = await res.json();

await fetch('https://your-server/api/admin/API_admin_create_battery.php', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': csrf_token },
  body: JSON.stringify({ battery_index, battery_name, tasks }),
});
```

*Why not `localStorage` for the CSRF token:* it doesn't need to survive a page reload (a fresh
login is cheap), and keeping it in memory only means an XSS bug elsewhere in the app can't read
it out of storage. The session cookie itself is `httpOnly`, so JavaScript can't read that either
way.

## Known gaps — not oversights, but not built yet

These were left out to keep the first version reviewable; add them before this handles real
lab data from outside your own machine:

- **No login rate limiting.** `API_admin_login.php` will happily accept unlimited attempts per
  second. For a handful of known lab-staff accounts this is a lower-severity gap than it would
  be for a public login, but still worth adding (e.g. a failed-attempts counter per username
  with a short lockout, or fail2ban at the web-server level watching for repeated 401s).
- **No audit log.** Nothing currently records *which* admin created a given battery/parameter
  set, or when. If more than one person will use this UI, consider adding a `created_by`
  column (FK to `admin_users`) to `batteries`/`task_parameters`/`task_instructions`.
- **No "update" or "delete" endpoints.** Only `create_*`. This was a deliberate scope decision
  (see `DiscussionLog.md`) — editing/removing existing parameter sets that other batteries may
  already reference needs its own careful design (what happens to a battery using a parameter
  set someone just changed?), not a quick addition to this API.
- **Session lifetime is PHP's default** (`session.gc_maxlifetime`, typically 24 minutes of
  inactivity). Fine for a low-traffic internal tool; revisit if that's annoying in practice.
