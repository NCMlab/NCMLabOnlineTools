## Problem Statement

`Batteries/Batteries.js` specifies a list of batteries (study sessions). Each battery contains
an ordered list of tasks. Each task entry references:

| Field | Example | File it points to |
|---|---|---|
| `Task` | `"Word Recall"` | `html/JATOS/WordRecall.html` |
| `Parameters` | `"RAVLT_Spoken_Immediate"` | `config/WordRecall_Setup.js` (named JS object) |
| `Instructions` | `"Default"` | `InstructionsAndStimuli/Instructions/WordRecall_Instructions.js` |
| `IconName` | `"Immediate"` | Display label only |

This file-based approach has become bulky and hard to maintain. The goal is to move all
configuration into a MySQL database.

## Database Design

### Design Decision: JSON Columns for Parameters and Instructions

Because each task type has a completely different parameter schema, storing parameters as
rows (key-value pairs) would require many sparse rows or a complicated EAV schema. Instead,
we store the full parameter object as a JSON column. MySQL 5.7.8+ supports native JSON.
The HTML task code already consumes these objects wholesale, so a JSON blob is a natural fit.

---

### Table 1: `task_types`
Catalog of all available task types. One row per task type.

```sql
CREATE TABLE task_types (
    task_type_id   INT           AUTO_INCREMENT PRIMARY KEY,
    task_name      VARCHAR(100)  NOT NULL UNIQUE,   -- e.g. "Word Recall"
    html_file      VARCHAR(255)  NOT NULL,           -- e.g. "html/JATOS/WordRecall.html"
    icon_file      VARCHAR(255),                     -- e.g. "assets/Icons/WordRecall.png"
    created_at     TIMESTAMP     DEFAULT CURRENT_TIMESTAMP
);
```

---

### Table 2: `task_parameters`
Each row is one named parameter set for one task type.

```sql
CREATE TABLE task_parameters (
    parameter_id    INT           AUTO_INCREMENT PRIMARY KEY,
    task_type_id    INT           NOT NULL,
    parameter_name  VARCHAR(150)  NOT NULL,   -- e.g. "RAVLT_Spoken_Immediate"
    language        CHAR(2)       DEFAULT 'EN',
    parameters_json JSON          NOT NULL,   -- full parameter object as JSON
    created_at      TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_task_param (task_type_id, parameter_name),
    FOREIGN KEY (task_type_id) REFERENCES task_types(task_type_id)
);
```

---

### Table 3: `task_instructions`
Each row is one named instruction set for one task type.

```sql
CREATE TABLE task_instructions (
    instruction_id    INT           AUTO_INCREMENT PRIMARY KEY,
    task_type_id      INT           NOT NULL,
    instruction_name  VARCHAR(150)  NOT NULL,   -- e.g. "Default"
    language          CHAR(2)       DEFAULT 'EN',
    instructions_json JSON          NOT NULL,   -- full instruction object as JSON
    created_at        TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_task_instr (task_type_id, instruction_name, language),
    FOREIGN KEY (task_type_id) REFERENCES task_types(task_type_id)
);
```

---

### Table 4: `batteries`
One row per battery (study session configuration).

```sql
CREATE TABLE batteries (
    battery_id            INT           AUTO_INCREMENT PRIMARY KEY,
    battery_index         INT           NOT NULL UNIQUE,   -- the numeric lookup key
    battery_name          VARCHAR(100)  NOT NULL,          -- e.g. "H-10-23-9755"
    description           VARCHAR(255),
    battery_instructions  TEXT,                            -- welcome text shown to participant
    language              CHAR(2)       DEFAULT 'EN',
    run_audio_test        TINYINT(1)    DEFAULT 0,
    footer                VARCHAR(255),
    short_name            VARCHAR(50),
    header_buttons        JSON,                            -- e.g. ["Quit","Stop"]
    languages_to_show     JSON,                            -- e.g. ["EN","FR"]
    redirect_url          VARCHAR(500),
    active                TINYINT(1)    DEFAULT 1,
    created_at            TIMESTAMP     DEFAULT CURRENT_TIMESTAMP
);
```

---

### Table 5: `battery_tasks`
Join table: ordered list of tasks within each battery.

```sql
CREATE TABLE battery_tasks (
    battery_task_id   INT           AUTO_INCREMENT PRIMARY KEY,
    battery_id        INT           NOT NULL,
    task_type_id      INT           NOT NULL,
    sort_order        INT           NOT NULL,   -- position in the task list (1-based)
    parameter_id      INT,                      -- FK to task_parameters (NULL if no params)
    instruction_id    INT,                      -- FK to task_instructions (NULL if no instr)
    icon_name         VARCHAR(100),             -- display label, e.g. "Immediate"
    FOREIGN KEY (battery_id)    REFERENCES batteries(battery_id),
    FOREIGN KEY (task_type_id)  REFERENCES task_types(task_type_id),
    FOREIGN KEY (parameter_id)  REFERENCES task_parameters(parameter_id),
    FOREIGN KEY (instruction_id) REFERENCES task_instructions(instruction_id)
);
```

## How HTML Files Will Communicate with the Database

### Architecture: REST API Middleware

HTML study components (running in JATOS in the participant's browser) cannot connect directly
to MySQL — browsers have no MySQL driver. The standard solution is a thin REST API layer
running on the server that the HTML pages call with `fetch()`.

**Recommended stack:** PHP (already available on most Linux servers) or Node.js/Express.

#### Request flow:
```
Browser (JATOS study HTML)
    |
    | fetch('https://yourserver.ca/api/battery.php?index=16')
    v
REST API (PHP or Node.js on your server)
    |
    | SELECT * FROM batteries WHERE battery_index = 16
    | SELECT * FROM battery_tasks WHERE battery_id = ...
    | SELECT parameters_json FROM task_parameters WHERE ...
    | SELECT instructions_json FROM task_instructions WHERE ...
    v
MySQL database
    |
    v
API assembles JSON response, returns to browser
    |
    v
Browser JavaScript parses JSON, runs study as before
```

#### Example API response (replaces current BatteryList entry):
```json
{
  "battery_index": 16,
  "battery_name": "H-10-23-9755",
  "language": "EN",
  "run_audio_test": true,
  "footer": "©NCMLab 2025",
  "header_buttons": ["Quit","Stop"],
  "redirect_url": "https://...",
  "tasks": [
    {
      "task_name": "Word Recall",
      "html_file": "html/JATOS/WordRecall.html",
      "icon_name": "Immediate",
      "parameters": { ...RAVLT_Spoken_Immediate object... },
      "instructions": { ...EN_Instructions_Default object... }
    },
    ...
  ]
}
```

See files: `API_battery.php` and `API_example_fetch.js` for implementation.

## 2026-07-08 — Migration Script

> **Authorship notice:** this section generated by **Claude Code (model: claude-sonnet-5)**.

Built and ran an automated extractor for the two remaining bulk-migration items (task
parameters, task instructions) instead of hand-writing `JSON_OBJECT(...)` INSERTs as was done
for the one Word Recall example.

**Why not regex/text parsing:** the config/instruction files are not uniform — some are single
object literals (`var X = {...}`), some build the object via dot-assignment
(`X.Field = ...`), some alias one object to another (`CardSort_002 = CardSort_001`), some push
onto arrays. Regex parsing would need a special case per pattern and would silently mis-handle
the rest. Instead `migrate/extract.js` actually **executes** each file inside a Node `vm`
sandbox, stubbing the runtime's own `add(key, fn)` registration function (see
`functions/GeneralPurposeFunctions/pseudoSwitch.js`) to capture `{key, fn}` pairs without
running them yet. It then calls each `fn` and reads back whichever conventional variable
(`parameters` or `Instructions`) it set — the exact mechanism `pseudoSwitch()` uses at runtime,
so the extracted value is guaranteed to match what the browser would actually load.

Two runtime dependencies had to be reproduced for this to work:
- Every HTML page loads `config/General_Setup.js` before a task's own config/instructions
  files (defines shared globals like `StimulusFontSize`, `LabelNames`) — the extractor now
  preloads it into the sandbox first.
- A few instruction files reference `BaseFolderName`, which pages set inline via
  `<script>var BaseFolderName = '...'</script>` right before loading the instructions file —
  harvested by hand per file into `BASE_FOLDER_NAME_BY_FILE` in `extract.js`.

**Result:** 227 of 241 registrations extracted cleanly and validated as JSON; 14 are
*pre-existing bugs* in the current `.js` source (an `add()` callback referencing a variable
that is never defined anywhere in that file — e.g. all 7 registrations in
`SelfReport_Setup.js` reference undefined `stai`/`nfc6`/`nfc10`/etc.). These would throw a
`ReferenceError` today if anything ever called `pseudoSwitch()` on them — the migration didn't
create these gaps, it just surfaced them.

`migrate/generate_sql.js` turns the 227 clean extractions into `Migrated_TaskConfig.sql`
(`INSERT IGNORE`, so it's safe to re-run) by mapping each file's basename to a `task_types.task_name`.
189 of the 227 had a confident mapping to an existing task_types row. The other 38 fall into
two buckets, both written to `MANUAL_REVIEW.md` rather than guessed at:
- **10 files** (`Cancellation`, `EQ5D`, `ImageCopy`, `ReadingListening`, `Stroop` — config +
  instructions each) reference task types that don't exist in `task_types` yet. Either these
  need new `task_types` rows (with an HTML file) or they're deprecated/unused and can be
  dropped.
- **10 registrations** in `General_Setup.js` (LabelNames) and `SessionChooser_config.js`
  (session-picker page config) are real data but aren't a single task's parameter/instruction
  set — they don't belong in `task_parameters`/`task_instructions` as currently designed. Open
  question: does `LabelNames` need its own table (e.g. `ui_labels`), or does it stay in a
  shared JS file loaded independently of the per-task config?

**Not yet done:** applying `Migrated_TaskConfig.sql` to a real database, resolving the 38
manual-review items, and the `vDMS → Verbal DMS` mapping is a medium-confidence guess that
should be confirmed.
